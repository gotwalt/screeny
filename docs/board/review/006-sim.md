## Goal

A host program that is indistinguishable from the device on the network, so senders
can be developed and tested with no hardware, and so we have a second, independent
implementation of the receiver side of `docs/design/protocol-v1.md` to shake out spec
ambiguities before the firmware (card 008) implements the same thing.

## Context

- Spec: `docs/design/protocol-v1.md`. Architecture: `docs/design/architecture.md`.
- Use `crates/proto` (`screeny-proto`, see its README) for ALL parsing, building and
  decoding. If you find yourself re-implementing wire logic, it belongs in proto - add
  it there (narrowly) and say so in your report.
- The receive rules are in spec section 3.3 (drain, newest wins, seq handling), 6
  (control ops, telemetry, piggybacked `STATS_REQ` replies), 7 (source lock, idle).
  Implement them as written; where the spec is ambiguous, pick, document, and fix the
  spec text in your branch.
- Panel look: round LED dots on black with gaps, sRGB -> linear -> 64 levels -> back
  (see `docs/design/generative-art-brief.md` section 5 "Build a faithful preview").

## Deliverables

`crates/sim` (package `screeny-sim`, binary `screeny-sim`):

- Library: `SimDevice` that binds frame + control UDP ports (defaults 49374/49375, but
  configurable and able to bind port 0 for tests), runs the receive state machine,
  exposes the current displayed frame, counters and events through a handle. This is
  what integration tests drive.
- Binary, windowed mode (default): LED-dot rendering at >= 12x, title/overlay with fps
  shown, codec of last frame, bytes/frame, drops by cause, active source. Pick a
  window crate that builds cleanly on macOS arm64 (`minifb` or `pixels`+`winit`);
  keep it simple.
- Binary, `--headless`: no window; logs stats once a second; `--dump-dir` writes every
  Nth displayed frame as PNG; `--exit-after SECS`.
- mDNS: advertises `_screeny._udp` with the spec's TXT keys using the `mdns-sd` crate,
  instance name `screeny-sim` (configurable), so it never collides with the real
  device (`screeny`). `--no-mdns` flag for tests.
- Fault injection for sender testing: `--drop PCT`, `--delay-ms MS`, `--decode-ms MS`
  (pretend the device is slow, so `frames_dropped_superseded` rises).
- Control ops: all of them. `SET_WIFI`/`REBOOT` are accepted and logged, not acted on.
  Brightness affects the rendering. Idle behaviour per spec (hold, then status screen).
- Tests: in-process sender (built directly on proto, a few lines) streaming every
  codec to a `SimDevice` on loopback and asserting the displayed frame is bit-exact;
  seq wrap, stale/duplicate rejection, source lock + takeover after timeout, `FINAL`
  releasing the lock, `STATS_REQ` reply contents, every control op, malformed packets
  counted not crashed.

## Acceptance

`cargo test -p screeny-sim` passes; `cargo run -p screeny-sim` shows a window that
displays frames sent by any spec-conforming sender; `dns-sd -B _screeny._udp` lists it.

## Log

### 2026-09-19 - built, on branch `card/006-sim`

`crates/sim` (package and binary `screeny-sim`) is done and every acceptance
criterion holds: `cargo test -p screeny-sim` passes 97 tests, `cargo run -p
screeny-sim` opens a window that draws frames from a spec-conforming sender,
and `dns-sd -B _screeny._udp` lists `screeny-sim` next to the real `screeny`.
No serial port, no camera, no packet sent to 192.168.7.221.

**Shape of it.** `core.rs` is the whole receive state machine with no I/O and
no wall clock in it - every method takes `now_us` - and `device.rs` is two
sockets, three threads and a `Mutex<Core>`. That split paid for itself twice
over: `tests/core_rules.rs` checks `LOCK_MS` and `HOLD_MS` to the microsecond
instead of sleeping, and uses two senders on different IPs, which is the case
section 7.4's "from any port on the same IP" is actually about and which
loopback will not hand out. Everything else is small: `stats.rs` (the counters
and EWMAs in the same integer arithmetic the firmware will use), `panel.rs`
(sRGB -> linear -> 64 duty levels -> sRGB), `screens.rs`, `font.rs`, `mdns.rs`,
`dump.rs`, `window.rs`.

**Seventeen spec ambiguities**, all fixed narrowly in
`docs/design/protocol-v1.md` and listed there as section 11 items 14-30. The
four that were closest to being real bugs:

- **`frames_rx` had two defensible meanings.** If it counts only displayed
  frames, section 6.9's whole diagnostic table collapses: a sender cannot tell
  a lossy network from a device that cannot keep up, because both look like
  "fewer frames than I sent". It has to count every *accepted* datagram,
  superseded ones included. Section 3.3 now states the identity
  `d(frames_rx) = d(shown) + d(superseded) + d(decode)` outright.
- **A sender restarting a stream could lock itself out forever.** Section 3.2
  said `seq` "MUST NOT be reset except when the sender restarts a stream" -
  but `last_seq` is kept per source, and a source is a 4-tuple, so a sender
  that restarted at 0 from the same socket would have every frame rejected as
  stale for up to 32767 frames. The permission has become a prohibition: rebind
  instead, which resets `last_seq` on the device for free.
- **`RELEASE` could not work as written.** Section 6.3 said "only if the
  requester currently holds it" and section 7.4 said "from any port on the same
  IP". A `RELEASE` arrives on the *control* port, so its source port is never
  the frame stream's; an exact 4-tuple match would have made the opcode dead on
  arrival. Matched on the IP.
- **Section 5.5's `GET_INFO` rate limit contradicted section 6.1's retry
  rule.** One reply per source per second, versus retry up to three times with
  the same `req_id` - a sender whose reply was lost would be stonewalled for a
  second with no way to tell that from a dead device. The limit now counts new
  requests and exempts a repeat of an already-answered `req_id`. It is also now
  written as applying to every `GET_INFO` rather than to broadcast ones only,
  because a receiver generally cannot tell which address a datagram was sent to
  without `IP_RECVDSTADDR`, and a rule two implementations read differently is
  worse than one that is slightly too strict.

The rest: `STATS_REQ` is answered for any admitted frame whether or not it is
shown (withholding it hides exactly the failure the sender is asking about);
`BUSY` leaves by the frame socket like `TELEMETRY`; the 100 ms telemetry limit
covers the piggybacked reply only; `BUSY`'s `lock_holder_ms_remaining` is
defined; `req_id == 0` silences error replies too; a `CONTROL` with `REPLY` set
is discarded; `ERR_BAD_LENGTH` is answered from the two header fields that are
certainly present; the section 6.8 EWMAs are seeded from the first interval
rather than eased up from zero; `interarrival_max_us` survives a source change;
`RESET_STATS` touches nothing but counters; a `FINAL` frame that fails to
decode releases nothing; `HOLD_FOREVER` keeps the state byte at `HOLD` while
`DIM` and `BLACK` reach `IDLE`; an over-1472-byte datagram is discarded rather
than parsed from its truncated prefix; `frames_rejected` counts the frame port
only.

**One addition to `crates/proto`:** `packet::peek(&[u8]) -> Option<RawHeader>`,
plus the `RawHeader` type. Purely additive, nothing renamed. Two places in the
spec need an `op` and a `req_id` out of a datagram `parse` has refused -
section 2.2's optional `ERR_VERSION` and section 6.5's `ERR_BAD_LENGTH` - and
without it the simulator would have had to re-implement the header. Vectors in
`crates/proto/tests/golden.rs`.

**Measured.** The bit-exactness tests stream all 27 of `crates/proto`'s
checked-in vectors over loopback and compare against the `.rgb` files, whose
pixels came out of the frozen card-002 lab and owe nothing to this crate or to
`proto`'s decoders. `tests/common/mod.rs` also carries hand-built encoders for
four of the five codecs, written from section 4's prose rather than from the
decoders, so a round trip through them checks two independent readings of the
codec spec against each other. The fifth, `BC1_DUAL`, is built there too with
its expected pixels computed from the spec's own `lerp` and weight tables.

Two small surprises worth recording:

- An **all-literal LZ stream does not fit**. 2048 index bytes as literals is
  2304 bytes of stream, well over the 1464-byte budget, so `PAL8_LZ` cannot be
  produced by a trivial encoder at all - the test helper needed a real greedy
  matcher. Worth knowing before card 009 writes the fast path.
- **`decode_us` and the `--decode-ms` fault.** The injected delay is added to
  the reported `decode_us` rather than only slept, because a simulator
  pretending to be a slow device should look slow in telemetry too. The sleep
  itself happens outside the core lock and after the buffer swap, so the *next*
  drain is the one that piles up - which is how `frames_dropped_superseded`
  rises for the right reason.

**Out of scope, written up rather than done:** cards 080 (lift the wire-level
rules into a conformance suite that can be pointed at the firmware too), 081
(model the Wi-Fi join states and the `PROVISIONING` overlay, which are the two
control paths a simulator with no radio never exercises) and 082 (the
generative-art brief's squint view and its four content numbers, the one part
of brief section 5 this card did not build).

**Left undone on purpose:** no ghosting, refresh banding or temporal dithering
in the preview (card 030 owns that); `SET_WIFI` and `REBOOT` are accepted,
logged and not acted on, as the card asked; `SET_BRIGHTNESS`, `SET_IDLE` and
`SET_NAME` are not persisted, which is moot while `REBOOT` is a no-op. The
simulator's brightness cap defaults to 255 rather than the firmware's, since
this panel is not running off laptop USB; `--brightness-cap` sets it for
testing how a sender learns the cap.
