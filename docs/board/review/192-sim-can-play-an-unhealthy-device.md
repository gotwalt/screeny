## Goal

`screeny-sim` should be able to report a panel that is **not** well: a brownout or a
panic as the reset reason, a firmware slot that is `pending_verify` or `invalid`,
settings-store errors, a nearly-full heap, a nearly-exhausted stack.

**This is `crates/sim`, which the firmware session owns.** Written here by card 180's
worker because that is where the gap was found; it is theirs to pick up or refuse.

## Context

- `crates/sim/src/api.rs::status` reports `FwSlot::Ota0`, `FwState::Valid` and
  `ResetReason::PowerOn` as constants, and `heap_used`/`heap_size`/`stack_free`/
  `store_errors` from `core::Ident`'s fixed values (64 KB of 96 KB, 20 KB, 0). The
  comment is honest about why: there is no flash and no reset to have a reason.
- Card 180 gave the Studio's page four things that are meant to stand out - a reset
  reason that is not a power-on or a reboot we asked for, `store_errors > 0`, a
  `fw_state` that is not `valid`, and memory running out - and **none of them can be
  produced by the simulator**. They are covered by unit tests over
  `crates/device-api/tests/golden/status.json` and by a hand-written test server in
  `crates/studio/tests/device_status.rs`, but the whole page has never been seen in its
  unhappy state against a device-shaped thing.
- That matters more than it sounds. These four are exactly the rows nobody will ever see
  in the ordinary course of things, so they are exactly the rows that will be wrong when
  they finally appear. The owner's panel reading `brownout` at three in the morning is
  the moment they have to be right.

## Deliverables

Flags on `screeny-sim` that set what `GET /api/v1/status` reports, with nothing else in
the simulator pretending they are real:

- `--reset-reason NAME` (any `screeny_device_api::ResetReason`)
- `--fw-slot`, `--fw-state`
- `--store-errors N`
- `--heap-used N --heap-size N`, `--stack-free N`

## Acceptance

`screeny-sim --headless --no-mdns --http-port N --reset-reason brownout --store-errors 3
--stack-free 900` answers a status with those values, and the Studio's page draws all
three in the fault tone. A screenshot of that page goes in the card's Log - it is the
only picture of the unhappy state anyone has.

## Log

### 2026-09-20, worker-192 (firmware session), branch `card/192-sim-unhealthy-device`

Accepted as written. Everything is in `crates/sim`; nothing outside it was touched.

**What it is.** `Health` (`crates/sim/src/config.rs`) is the seven values of
`GET /api/v1/status` a host cannot measure: `reset_reason`, `fw_slot`, `fw_state`,
`store_errors`, `heap_used`, `heap_size`, `stack_free`. It follows `Faults`, which is the
same shape of thing and already had the pattern: a struct in `config.rs`, a `Config`
field (`Config::health`), and a pair of `SimHandle` methods.

- **CLI:** `--reset-reason`, `--fw-slot`, `--fw-state`, `--store-errors`, `--heap-used`,
  `--heap-size`, `--stack-free`. `Health::default()` is exactly what the simulator
  reported before this card - `power_on` / `ota_0` / `valid` / `0` / `65536` / `98304` /
  `20480` - so a command line that does not mention them is byte-for-byte unchanged, and
  `..Config::default()` / `..Config::for_test()` keep compiling.
- **Library:** `SimHandle::set_health(Health)` and `SimHandle::health()`, both under the
  same one `Mutex<Core>` everything else uses. `Health` is `Debug + Clone + Copy +
  PartialEq + Eq` and is re-exported from the crate root.
- **`Ident` was extended, not replaced.** It already held four of the seven; it gained
  `reset_reason`, `fw_slot`, `fw_state` and the two methods `health()` / `set_health()`.
  Nothing was removed from the public API.

**Names come from the API, not from here.** `--reset-reason brownout` is parsed by handing
the string to `serde_json` *as* a `screeny_device_api::ResetReason`, so the simulator
cannot accept a name the firmware could not send. The list of names in the error message
is generated by asking serde for each variant's name; the three lists of variants are
guarded by three exhaustive `match`es, so a variant added to `crates/device-api` stops
`crates/sim` compiling rather than quietly going missing. A unit test in the binary makes
`--help` fail by name in the same case.

**Two CLI errors.** A name the API does not have, refused with every name it does have;
and `--heap-used` greater than `--heap-size`, refused rather than clamped - `screeny-probe`
HTTP rule 5 (`heap_used <= heap_size`) is a rule the simulator should pass honestly, and
silently fixing the numbers up would hide the typo that produced them.

**Nothing else pretends.** No behaviour anywhere reads these back: a `pending_verify` slot
changes nothing, `--store-errors 3` breaks no store, `--stack-free 900` runs nothing out of
stack. The one exception is the one the device has too, and it is deliberate: **a simulated
`REBOOT` - UDP `REBOOT` or `POST /api/v1/reboot` - sets the reset reason to `software` from
then on**, drawn in the same arm of `core.rs` that already draws the new `boot_id`, so both
paths get it by construction. `set_health` called *after* a reboot pins the reason again,
which is what lets a test show a `brownout` row at all. Written down in the README, in
`api.rs`'s module docs and in `Health`'s own docs.

**Evidence.** The acceptance command, by hand:

```
$ screeny-sim --headless --no-mdns --bind 127.0.0.1 --http-port 8099 \
      --reset-reason brownout --store-errors 3 --stack-free 900 --exit-after 8
screeny-sim: HTTP API on http://127.0.0.1:8099/
screeny-sim: health: reset brownout slot ota_0 state valid store_errors 3 \
             heap 65536/98304 B stack_free 900 B (reported, not simulated)
$ curl -s localhost:8099/api/v1/status
{"api":1,...,"heap_used":65536,"heap_size":98304,"stack_free":900,...,
 "fw_slot":"ota_0","fw_state":"valid","reset_reason":"brownout","store_errors":3}
```

**Tests.** `cargo test -p screeny-sim` is **140** (was 126): nine new in
`crates/sim/tests/health.rs` and five new unit tests in the binary. The new file pins the
seven defaults as numbers *and* as bytes on the wire; all seven flags reaching the status
reply through one spawn of the built binary on ephemeral ports; every variant of all three
enums round-tripping through its flag parser and back out under the name it went in as;
the two refusals; `set_health` on a running simulator and back again; the reboot rule over
HTTP and over UDP, a refused reboot not moving the reason, and `set_health` after a reboot
winning; and one test that says the other half out loud - an unhealthy status changes
nothing else about the device.

Both conformance suites are **unmodified and green**: `tests/conformance.rs` (1 test, the
64-rule UDP suite) and `tests/http_conformance.rs` (5 tests, the 38-rule HTTP suite).
`cargo clippy -p screeny-sim --all-targets` says nothing. The whole workspace - a plain
`cargo test` from the root, every crate and every doc-test - passed first time, including
`crates/screeny`'s soak and pacing tests, with no re-run needed.
