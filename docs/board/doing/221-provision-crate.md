## Goal

The part of WiFi provisioning that can be right before it ever meets a radio: a
`no_std`, no-alloc crate holding (1) the join/portal state machine as a pure function
of events and time, (2) the `WIFI:` QR payload builder with its length rule, and (3) the
portal screen renderer (QR + text into a 64x32 RGB frame). The firmware (card 223) and
the simulator (card 224) will both drive it; this card proves it on the host. It is the
same split `crates/receiver` made for the receive rules: no I/O, no clock, no
allocation, the caller passes `now_ms`.

## Context

Read first: `CLAUDE.md`, `docs/design/device-web.md` (decisions and the 201 summary),
then `docs/research/007-device-web-and-portal.md` sections 5 (the state machine: the
diagram and the transition table are the specification for this card), 8
(host-testability) and 9 (the QR and the three layouts; mock-ups in
`docs/research/img/201-portal-*.png`, generated by `lab/src/bin/portal-mock.rs`),
`crates/receiver/src/lib.rs` (the precedent: `Intent`s out, events in, clock-free),
`firmware/src/screens.rs` (how the device draws today: `embedded-graphics` with
`FONT_4X6` / `FONT_5X7` into an RGB frame), `firmware/src/web_spike/qr.rs` (card 201's
compile-only QR spike: evidence that `qrcodegen-no-heap =1.8.1` links, not code to
keep), spec sections 6.7, 7.3 and 8.

Decided - do not reopen:

- States: `Boot`, `Joining`, `Online`, `Portal`, `Trial`. Transitions per 007 section
  5.2, including: 3 join attempts (~45 s) then portal; a posted credential goes to
  `Trial` with **nothing committed** and the AP kept up; on success commit, hold the
  AP 30 s, then drop it; on failure back to `Portal` with a reason the page can show
  (`AuthError`, `NetworkNotFound`, `Other`); in `Portal`, every 10 minutes **if no
  client is associated to the AP**, retry the stored credentials (only when there are
  some); `Online` with the link down > 60 s goes to `Joining`; a `ButtonWipe` event
  from any state clears credentials and goes to `Portal`. The portal has no time limit.
  Compile-time credentials, when the build has them, are tried after the stored ones
  fail and before the portal is raised (spec 8.3's step 2).
- The machine emits **actions** for the firmware to carry out (`StartJoin{which}`,
  `RaiseAp`, `DropAp`, `CommitCredentials`, `ClearCredentials`, `Announce`, ...) and
  exposes what the rest of the system reads: the telemetry state overlay
  (`PROVISIONING` in `Portal` and `Trial`), the `GET_WIFI` state byte per 007 section
  5.2, which screen the panel should show, and the last trial result for the page.
  Timing constants are `pub const`s with the reasoning in a comment.
- QR: version 2, error correction L, byte mode, payload `WIFI:T:nopass;S:<ssid>;;`,
  which holds an SSID of at most 14 bytes. **Measured on the real panel and scanned by
  the owner's phone**: one LED per module, lit white background with dark modules off,
  3-pixel lit quiet zone, 31x31 block. Do not change polarity, module size or quiet
  zone. The AP name is always `screeny-<id>` (14 bytes). The builder must *refuse* an
  SSID that does not fit rather than silently move to version 3; escaping of `\ ; , : "`
  per the WiFi URI rules is implemented and tested even though `screeny-<id>` never
  needs it. (A later bench card may try the short form `WIFI:S:<ssid>;;`; make the
  form an enum so that is a one-line change.)
- The PSK never appears in `Debug` output, in an action's `Debug`, or on the screen.
- Layouts: A (QR left, `screeny-` / `<id>` and a short instruction in the 32 columns to
  its right, eight `FONT_4X6` characters per line) alternating with C (text only:
  "join wifi", the SSID, "then open", "192.168.4.1") on a slow timer the caller drives;
  after a successful trial the screen shows the acquired IP for 60 s. No full-white
  frame: the QR's lit area is 31x31 of 64x32 pixels at whatever brightness the device
  is set to, which the owner has already seen and accepted. Text is dim-white or a
  colour, not full white.

## Deliverables

1. `crates/provision/` (package `screeny-provision`), `#![no_std]`, no alloc, in the
   root workspace. Dependencies: `heapless`, `qrcodegen-no-heap =1.8.1`,
   `embedded-graphics` at the version `firmware/Cargo.toml` uses, and `screeny-proto`
   only for the existing `wifi_state` / telemetry state constants (read them, do not
   add to that crate).
2. The state machine with an exhaustive transition test table (every row of 007's
   table, plus: retry suppressed while a client is associated; retry not attempted with
   an empty store; trial failure leaves stored credentials untouched; compile-time
   fallback order; `ButtonWipe` from every state; time wrap of `now_ms: u32` at ~49.7
   days, because this device is meant to run unattended for months).
3. The URI builder and QR encoder wrapper, with tests: the exact 32-byte payload for
   `screeny-4a00a4`; a 15-byte SSID refused; escaping; and a decode check - add a
   dev-dependency QR *decoder* (e.g. `rqrr`) and prove the rendered 64x32 frame decodes
   back to the payload, so the renderer's polarity/quiet-zone/placement can never
   silently rot.
4. The renderer: `fn render(screen: Screen, frame: &mut [u8; 64*32*3])` or the
   equivalent with the workspace's existing frame type if one fits (look in
   `crates/proto` / `crates/panel`). Golden tests: write each layout as a PNG under
   `docs/research/img/221-*.png` (small files) from a test or example, and assert a
   stable hash of the frame bytes so an accidental layout change fails a test.
5. `crates/provision/README.md`: the state diagram, the action list, and how the
   firmware is expected to drive it (twenty to forty lines).

## Out of scope

Anything in `firmware/` (card 223 wires it in) or `crates/sim` (card 224). DHCP, DNS,
HTTP. `crates/proto`, `crates/receiver` and the spec are shared with the software
session and are **not** touched; if you believe one needs a change, write it in the Log.
